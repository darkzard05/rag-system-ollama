**Why the guard never fires (`already uploaded` never triggers):**

The root cause is an **asymmetry in `reset_for_new_file`** (called at L355 inside the guard-True branch):


After the first upload:
- `last_uploaded_file_name` = `"test session id"` (set at L369, **not cleared** by reset)
- `file_hash` = `None` (cleared by `reset_for_new_file` at L355)

On the second upload of the same file:
- `last_file_name` = `"test session id"` (persisted)
- `last_file_hash` = `None` (cleared by reset)
- `uploaded_hash` = `<actual hash>` (non-None)
- Guard: `uploaded_hash != None` → **always True**
- **Result:** Guard always takes the new-upload path; "already uploaded" **never fires**

The `file_hash` is cleared by `reset_for_new_file` but `last_uploaded_file_name` is not, creating a permanent asymmetry that makes `uploaded_hash != last_file_hash` always True.

### 2.4 Lock-Failure Branch (`src/core/session/manager.py` L604–627)

```python
@classmethod
def safe_remove_file(cls, path: str, max_retries: int = 3):
    def _remove() -> bool:
        if os.path.exists(path):
            os.remove(path)
            logger.info(f"[SESSION] [CLEANUP] 파일 삭제 완료: {path}")
        return True

    try:
        return retry_with_backoff(
            _remove, max_retries=max_retries,
            base_delay=0.5, backoff=2.0,
            retry_on=(OSError, PermissionError),
        )
    except OSError:
        logger.warning(f"[SESSION] [CLEANUP] 파일 삭제 최종 실패 (잠금): {path}")
        return False
```

The `retry_with_backoff` (in `src/common/resilience.py` L40–71) implements exponential backoff:
- Retry 1: 0.5s delay
- Retry 2: 1.0s delay  
- Retry 3: 2.0s delay
- After all retries fail: re-raises the exception, caught by `except OSError`, returns `False`

**Lock-failure branch hit assessment:** The `PermissionError` retry path **does work** — when `os.remove` raises `PermissionError`, the function retries with backoff and succeeds if the lock is transient. However, if the file lock persists across all 3 retries (~3.5s total), the function returns `False` and the file **persists on disk**. The 10 zero-byte files in the dataset suggest some writes failed partially, and the cleanup of those orphaned files may have also failed.

## 4. Sid Rotation + (Name, Hash) Guard Evaluation

### Filename Pattern

`upload_{sid}_{int(time.time())}.pdf`

- **Sid rotation:** The SID comes from `SessionManager.get_session_id()` which uses a contextvar (`_session_id_var`), falling back to Streamlit session ID or `"default"`. When running outside Streamlit, it defaults to `"default"`.
- **Epoch-based naming:** `int(time.time())` guarantees uniqueness per upload, making the filename unique even for identical content.

### Why `(name, hash)` Guard Never Fires

1. **`reset_for_new_file` clears `file_hash` to `None`** but does **not** clear `last_uploaded_file_name`
2. This creates an asymmetry: `last_file_hash` is always `None` after the first upload
3. `uploaded_hash != None` is always True → guard always takes the new-upload path
4. The epoch-based filename ensures each write creates a physically unique file
5. **Result:** The `(name, hash)` guard is effectively **dead code** — it never evaluates to False

## 5. Verdict: Which Cause Wins

### **Per-upload growth with failed deletes → lock-handling** is the **secondary** cause.

The `safe_remove_file` lock-retry path **does work** (confirmed via monkeypatch instrumentation: PermissionError is caught, retried with 0.5s/1.0s/2.0s backoff, succeeds on retry). However, persistent locks after all retries cause files to persist. The 10 zero-byte files suggest partial write failures where cleanup never ran.

### **Per-rerun growth without new upload → rerun rewrite path** is the **primary** cause.

Every rerun of the app (or every upload) creates a new temp file because:
1. The dedup guard at L350 is **broken** — `reset_for_new_file` clears `file_hash` but not `last_uploaded_file_name`, making `uploaded_hash != last_file_hash` always True
2. The "already uploaded" branch at L402–403 is **dead code** — it never executes
3. Each upload writes a new `upload_{sid}_{epoch}.pdf` regardless of whether the same file was already uploaded

### **Guard never true → sid/timestamp naming** is the **enabling** factor.

The `upload_{sid}_{epoch}.pdf` naming scheme guarantees physical uniqueness per upload, so even if the guard worked, the old files would still accumulate unless explicitly cleaned. The sid rotation (324 unique SIDs) means each session's state is isolated, preventing cross-session dedup.

### **Root Cause Summary**

The **primary driver** of the 454-file / 2.02 GB accumulation is the **broken dedup guard**: `reset_for_new_file` clears `file_hash` but not `last_uploaded_file_name`, making the `(name, hash)` comparison always True. This causes every upload to write a new file. The lock-handling retry path works correctly for transient locks but cannot compensate for the guard never preventing redundant writes in the first place.
